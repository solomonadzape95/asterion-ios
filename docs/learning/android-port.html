The Android port

This is written for a first mobile app, full stop — no assumed Android, iOS, or general mobile background. Read this before touching AsterionAndroid code.

The big picture, before any code

Asterion already exists as two apps: AsterionMac (a Mac app, written in Swift) and an iOS app (also Swift). Both talk to the same backend server over the internet — a service running on Node.js that knows about novels, anime, movies, and football data, and that speaks a language called HTTP: send it a request, it sends back a response, usually as JSON text.

An Android app is a third, completely separate app, written in a different language (Kotlin) using different tools, that talks to that same backend. Nothing about the backend needs to change for Android to exist — it's just another client making the same kind of requests a web browser or the Mac app already makes.

HTTP request/response, in plain terms An app asks the backend a question by sending a small text message over the internet (a "request"): which URL, which action (usually GET to read, POST to write), and sometimes a body of data. The backend answers with a "response": a status number (200 means "ok, here's your data"; 404 means "not found") and usually a JSON body — text formatted like {"ok": true} that both sides agree on how to read.

What had to exist before any Asterion code could run

Three pieces of tooling had to be installed on this Mac first, none of which are specific to this app — every Android app needs them:

What a build system actually does

Source code you write (.kt files) is not what runs on a phone. A phone runs a packaged file called an APK — your compiled code, plus every external library your code depends on, plus images and resource files, all zipped together with instructions for how to install and launch it. Gradle's job is turning your loose source files into that one APK, automatically, every time you ask it to build.

Part of that job is fetching your dependencies — external code you didn't write yourself (a networking library, a UI toolkit) — from the internet, from shared repositories (like an app store, but for code libraries instead of apps). You declare what you need by name and version; Gradle downloads it, checks it's compatible, and links it in.

What an emulator proves that a successful build does not

Gradle succeeding only proves the code is well-formed enough to package. It says nothing about whether the app actually starts, draws a screen, or can reach the internet. The emulator is a virtual phone; installing and launching the APK there, and watching what it actually does, is the only way to know the app works — the same reason AsterionMac's build script has a --verify step that launches the real app, not just compiles it.

How the pieces of AsterionAndroid fit together

Four ideas carry almost the entire app so far. Understanding these four generalizes to every screen added later — the specific files are just where these ideas happen to live today.

1. Compose: the UI is a function of state, not a series of manual updates Older UI frameworks (including Android's original one) work like: create a text label, later reach back into it and manually change its text when something happens. Jetpack Compose works differently — you write a function that describes what the screen should look like given the current state, and Compose re-runs that function (called "recomposing") automatically whenever the state it reads changes. You never manually update a label; you just change the state, and the UI catches up.
2. ViewModel: state that survives the screen being recreated Android can destroy and recreate a screen for reasons that have nothing to do with your logic — rotating the phone, low memory. A ViewModel is a holder object that Android guarantees survives that recreation, so it's the correct place to keep "what is currently true" (like: is the network call loading, succeeded, or failed) separate from the disposable screen itself.
3. StateFlow: a box that announces when its contents change A StateFlow is a value holder that a UI can "subscribe" to — anyone watching it is automatically notified the instant the value inside changes, which is exactly the trigger Compose needs to know when to recompose. It's the wiring between "the network call finished" and "the screen updates," and nobody has to manually push that update through.
4. Koin: a directory that hands out shared objects instead of each screen building its own Things like the network client should exist exactly once for the whole app, not be rebuilt by every screen that needs one. Koin is a small library that builds those shared objects once, up front, and hands the same instance to whoever asks — this pattern in general is called dependency injection: instead of a piece of code constructing what it needs itself, something else constructs it and hands it over.

Walking through what happens when the app opens

Nowhere in that chain does anything say "now update the label." The StateFlow change is enough — Compose is watching it, and reacts automatically. That's the entire point of the reactive pattern above.

Adding sign-in

"Auth" (short for authentication) is how the app knows which person is using it, so it can show their library and reading progress instead of a stranger's. Asterion doesn't run its own sign-in system — it uses Clerk, a separate hosted service that handles passwords, email codes, and "Sign in with Google/Apple" so this app never has to store a password itself. AsterionMac already uses Clerk; the Android app now signs into the exact same accounts, because both apps point at the same Clerk project.

Why use a prebuilt sign-in screen instead of building one Auth screens look simple but hide real complexity: validating input, showing the right error for a wrong password vs. an unverified email, handling "forgot password," handling two-factor codes, keeping the session alive correctly. Clerk ships a ready-made screen (AuthView) that already handles all of that, wired directly to Clerk's backend — one line of code (AuthView()) instead of building and maintaining that whole flow by hand.

The whole decision of what to show the user boils down to one question, asked every time the screen recomposes: is anyone signed in right now? Clerk itself keeps the answer as a StateFlow (the same reactive box from idea 3 above) — nothing app-specific has to track it.

This is exactly the same when { } pattern used for BackendStatus earlier — one state holder, one place that decides what's on screen, no manual UI updates. AsterionRoot reads Clerk.isInitialized and Clerk.userFlow directly; it doesn't need its own ViewModel, because Clerk already exposes shared, observable state — wrapping it in another layer would just be indirection with nothing added.

Browsing novels: screens, and moving between them

So far the app has only ever shown one screen at a time, decided once by AsterionRoot. Real apps need many screens, entered and left in response to taps, with a working back button — a novel list, a novel's detail page, a chapter's text. The tool for that is a navigation graph: a map of named "routes," each tied to a screen, plus rules for how the app can move between them.

Each route can carry a piece of data in its name — novels/{id} means "show the detail screen, and here is which novel." Tapping a novel in the list calls navController.navigate("novels/935"); the detail screen reads 935 back out of its own route. The back button is not custom code anywhere in this app — the navigation library keeps a stack of visited routes automatically and pops one off whenever the system back gesture fires.

Why the list only ever shows a handful of rows in memory A novel catalog could have thousands of entries, but the phone screen only ever shows a dozen or so at once. LazyColumn (used for both the novel list and the chapter list) only builds the rows currently visible on screen, plus a small buffer — as the reader scrolls, rows that leave the top are thrown away and new ones are built for what's newly visible. This is why it's called "lazy": work is deferred until a row is actually about to be seen, which is why the same list pattern stays fast whether there are 20 novels or 20,000.

Each network response arrives wrapped one level deeper than the actual data — {"data": [...] } for lists, {"data": {...}} for a single item — because the backend also wants room to attach pagination info. Rather than write a separate wrapper class per screen, one generic ListEnvelope<T> and ItemEnvelope<T> unwrap any response shape the same way, whether T is a Novel or a Chapter.

Chapter text arrives from the backend as HTML (<p>paragraph</p>), because it was originally scraped from a web page. The reader screen strips every HTML tag with one regular expression before displaying it as plain, serif-styled text — good enough for a first version, though a regex is a blunt tool that would mishandle more complex markup than simple paragraph tags.

Watching anime: a second backend, and what streaming video actually is

Anime doesn't come from the same place novels do. Novels are Asterion's own database; anime is scraped live from a separate service (asterion-scraper.cyberverse.cloud) that talks to a third-party anime site on the app's behalf. Same app, same phone, two entirely different backends — the app just needs a second address book entry (a second Retrofit client, pointed at a different base URL) to talk to it.

What a video file actually being "streamed" means Video isn't sent as one giant file the way a chapter's text is. It's split ahead of time into many short segments (a few seconds each) plus one small text file — a playlist, ending in .m3u8 — listing where every segment lives and in what order. The player downloads the playlist first, then fetches segments one at a time, just far enough ahead to stay smooth. This is why video can start playing in a second or two instead of waiting for the whole episode to download, and why poor connections can drop to a lower-quality playlist mid-episode without restarting playback.

Media3 (Google's current video library, formerly called ExoPlayer) is the piece that understands .m3u8 playlists, fetches segments, decodes video and audio, and hands finished frames to a surface on screen. The player itself lives inside the ViewModel, not the screen, for the same reason HomeViewModel holds backend status — it must survive Compose recomposing the screen around it, and it must be explicitly shut down (player.release()) when the screen is really gone, or it keeps decoding video nobody can see.

The bug that revealed how the video is actually protected

The first working version showed a black screen with no crash — the least informative kind of failure, because nothing announces what went wrong. Reading the player's own error log (not just watching the screen) revealed the real story, in two layers:

  1. First symptom: the request for playback links timed out. The /stream/{id}/{episode} endpoint doesn't look anything up in a database — it visits the anime site live, right at the moment of the request, and hands back whatever links it finds. That can genuinely take longer than a typical API call, so the network client's timeout was raised to match what AsterionMac already relies on for this exact situation.
  2. Second symptom, only visible once the first was fixed: the video CDN answered every direct request with 403 Forbidden. The video host checks where a request claims to be coming from (a Referer header) and rejects anything that isn't its own web player — a common anti-hotlinking measure, not a bug in this app. The fix wasn't in the Android code at all: the scraper backend already runs a proxy (/proxy/m3u8) that re-requests the video with the header the CDN expects and relays it back. Routing playback through that proxy URL instead of the raw one — exactly what AsterionMac's Swift code already does — is what made the picture appear.

Neither layer was visible until the one in front of it was cleared. That's normal, not a sign of doing something wrong — a fixed bug often just reveals the next one waiting behind it, and the way to make progress is to keep reading the actual error, not to guess.

The player is intentionally minimal for this first version — it autoplays and shows the picture, but has no custom pause/seek bar yet. Media3's newest Compose controls are "headless" (they hand back play/pause state and expect the caller to draw the button), which is real work worth doing as its own next step rather than folding in unreviewed.

Watching movies: a third backend, and a security wall specific to Android

Movies are a third, independent backend (asterion-movies.cyberverse.cloud) — novels, anime, and movies each genuinely live somewhere different. The shape is even simpler than anime's: one request for a title's detail page already includes its playable stream links inline, no second request needed. The video itself is still an HLS playlist proxied the same way anime's was — that concept doesn't need re-explaining, but a new problem showed up in it.

Android refuses plain HTTP by default — on purpose Since Android 9, apps cannot make an unencrypted (http://) network request unless they explicitly say it's expected, for a specific set of hosts. This exists to stop exactly the kind of security hole plaintext HTTP allows — anyone sharing the same network, like public WiFi, could otherwise read or tamper with the request. An app opts a host back into cleartext deliberately, in one file (a "network security config"), naming precisely which host and never the whole internet — the point is to keep the default safe while making a narrow, visible exception for one known case.

That "known case" here: the movies proxy sometimes rewrites its own playlist's internal links as http:// instead of https:// — a bug in that service, not something this app's code produces or controls. Those links do still work; the server immediately redirects them to the correct https:// address. Two separate things had to both be true to make that redirect actually succeed:

  1. Android had to be told this one host is allowed to be asked over plain HTTP at all (the network security config) — otherwise the request never leaves the device.
  2. The video player had to be told it's allowed to follow a redirect that changes from http:// to https:// mid-request — by default it refuses that too, as its own, separate safety check.

Skipping either one reproduces the same failure a different way: skip the first, and Android blocks the request outright; skip the second, and the player receives the redirect but declines to follow it. Both had to be fixed together, and the log for each said exactly which one was still missing.

Watching football: a fourth shape of API, and a wall this page doesn't fully solve

Football is a fourth backend (asterion-football.cyberverse.cloud), and it wraps its responses in yet another shape: {"success": true, "data": [...] }. Novels used {"data": ..., "meta": ...}. Anime returned a bare array. Movies nested streams inside the show itself. Four features, four different envelope shapes — the real lesson isn't any one of them, it's that you check each API's actual shape every time; nothing about "it's JSON" tells you which wrapper a given backend chose.

GET vs. POST, in plain terms Every request so far has been a GET — "give me data," with everything needed to answer already in the URL. Resolving a match's streams is the first POST in this app: the match's raw source list has to be sent to the server as a request body, because the server doesn't store it — it takes those sources, resolves each one into a real playable link, and hands the results back. GET asks a question; POST asks the server to do something with data you're handing it.

The schedule listing and stream-resolution both work end-to-end with real data — a real match list, a real POST that returns real per-language, per-quality stream options. The last step is where this page is honest about a real, unresolved wall: these streams are embed URLs — full ad-supported web pages meant to be shown the way a browser shows any other site, not a video file ExoPlayer can decode. That calls for Android's WebView, a real embedded browser engine, instead of the video player used for anime and movies.

Loading the embed page surfaced two real, fixable gaps between a WebView and an actual browser: Android's WebView disables localStorage by default (the page's own script crashed reading from it — a normal browser never disables this), and WebView's default identity string contains a "; wv)" marker that flags it as an embedded view rather than a real browser, which some sites use to refuse to run at all. Fixing both was real progress — but a third, still-unidentified check in this specific embed provider's script keeps refusing to play, showing a generic "remove sandbox attributes" message that doesn't precisely describe what's actually being detected. That third layer is not resolved in this pass.

Why this is reported honestly instead of marked "done" Two real, understood problems got fixed with real evidence for each. A third one — inside a third-party site's own obfuscated anti-bot script — remains. Calling that "working" because the easier parts succeeded would be the wrong lesson to take from this project. The correct instinct when a fix doesn't fully land is the same one used everywhere else on this page: report exactly how far it actually got, not how far it was supposed to get.

Why these specific tools, out of the many options

Every one of these had at least one real alternative. None of the choices below are the only correct answer — they're reasonable defaults for learning, with a genuine runner-up noted.

ChosenIn plain termsRunner-up, and why it lost here
Retrofit + OkHttpTurns "call this URL" into a plain Kotlin function call — you never hand-write the HTTP request text yourself.Ktor: more modern, but Retrofit has more tutorials and clearer error messages for a first project.

What actually went wrong while building this, and why it matters

Every one of these was discovered by an error message, not predicted — that's normal, and the fix is usually more informative than getting it right on the first try.

What brokeThe underlying lesson
Build failed: org.jetbrains.kotlin.android plugin no longer allowedTools evolve out from under tutorials. This project uses a very recent version of the Android build tooling (AGP 9), which absorbed Kotlin support into itself — a plugin that used to be required is now actively forbidden. The fix was to delete it, not add anything.
Build failed: duplicate classes from two Clerk librariesA library's version number is not always sequential in the way you'd expect. clerk-android version 0.1.24 looked newer than nothing, but it was actually an abandoned early artifact — the real, current SDK had been renamed and split into two other library names entirely (clerk-android-api and clerk-android-ui) at version 1.0.x. The error (two libraries defining the exact same class) was the clue that pointed at this.
Build failed: needs API level 37, only 36 installedThe Android SDK version your code compiles against (compileSdk) is separate from the oldest phone your app supports (minSdk, set to 26 here — Android 8.0, released 2017). Libraries can require a newer compileSdk to build against, even while your app still happily installs on much older real phones.
Emulator creation failed: couldn't find a device profileAn "AVD" (Android Virtual Device) needs two things: a system image (the actual Android OS to run) and a device profile (screen size, RAM — what phone it's pretending to be). The very newest command-line tools had a bug reading device profiles for this exact system image; skipping the device-profile flag entirely let it fall back to a sane default and just work.
Clerk's own docs didn't show the prebuilt UI's real function signatureDocumentation can lag behind what a library actually ships. Rather than guess, the downloaded library file itself (an .aar, really a zip of compiled code) was unzipped and inspected directly with a Java bytecode tool (javap) to read AuthView's real, current parameters straight from what Gradle had already downloaded — the most reliable source available, since it's exactly what the app compiles against.
Build failed: TopAppBar is "experimental"Some Compose APIs ship marked experimental — usable, but flagged so a library can still change them later without warning. Using one requires explicitly opting in (@OptIn(ExperimentalMaterial3Api::class)) on the function that uses it — an intentional speed bump, not a bug, so nobody adopts a shifting API by accident.
Anime playback: black screen, no crash, request to fetch playback links timed outA silent failure is the hardest kind — nothing on screen says what's wrong, so the fix has to start from the error log, not the UI. The /stream endpoint scrapes a third-party site live per request rather than reading a database, so it can legitimately take longer than the default 10-second network timeout; the client's timeout was raised to 60 seconds to match what AsterionMac already relies on for this exact endpoint.
Anime playback: still a black screen after the timeout fix, now with a logged 403 ForbiddenFixing one error can uncover the next one hiding behind it — that's normal, not a sign of a wrong approach. The video CDN rejects any request that doesn't claim to come from its own web player. The backend already runs a proxy built for exactly this; routing playback through it instead of the raw video URL (matching what AsterionMac already does) resolved it.
Movie playback: black screen, "Cleartext HTTP traffic ... not permitted"Android blocks plain HTTP by default since Android 9 — a deliberate security default, not a bug to route around broadly. The movies proxy's playlist rewriting occasionally emits an http:// link that immediately redirects to https://; the fix was a narrowly-scoped exception for that one host, not disabling the protection everywhere.
Movie playback: same symptom persisted even after allowing cleartext for that hostA second, independent safety check existed one layer deeper: the video player itself refuses to follow a redirect that changes protocol (http→https) unless told to, regardless of what the OS permits. Two separate "no"s had to both become "yes" — permission from Android, and permission from the player — before the redirect could actually complete.
Football embed: page crashed reading from storage that returned nulllocalStorage is something every real browser provides by default; Android's WebView specifically disables it unless told otherwise. A page written assuming normal browser behavior will crash the instant it assumes storage exists. Enabling domStorageEnabled matched WebView's behavior to what the page already assumed.
Football embed: still refused to play after the storage fix, showing "remove sandbox attributes"WebView's default identity string contains a marker flagging it as an embedded view, which some sites use to refuse outright; removing it was a second real, understood fix. A third check inside this specific provider's own script still blocks playback and was not identified in this pass — reported honestly as unresolved rather than papered over.

How this was actually proven to work

A build succeeding is not proof an app works — it only proves the code is well-formed. What actually proved it:

  1. An emulator (virtual phone) was created and started.
  2. The real APK was installed onto it and launched, exactly like a phone owner tapping the icon.
  3. adb logcat — a live stream of everything happening inside the running app — showed a real network call complete: 200 https://asterion-api.cyberverse.cloud/health. That URL is the actual production Asterion backend, the same one AsterionMac talks to.
  4. A screenshot of the running emulator showed the words "Backend reachable" on screen, matching what the code was supposed to display for that outcome.
  5. After wiring Clerk, the app was reinstalled and relaunched the same way; a second screenshot showed a real "Continue to Asterion" sign-in screen — email field, Apple/Google buttons, a "Development mode" badge confirming it's genuinely talking to Clerk's dev servers with the dev key, not just rendering static placeholder text.
  6. The novels feature has no test Clerk account available in this environment to sign in with, so the code that decides which screen to show after sign-in (AsterionRoot) was temporarily edited to skip straight past the sign-in check, purely to prove the screens themselves work — then reverted immediately afterward, with a final build confirming the real, auth-gated code still compiles. This is the same thing a developer does locally when testing a screen before the login flow is ready; it was never committed.
  7. With that temporary bypass, five real screenshots were taken tapping through the actual live path: Home → Novels (real cover art and titles from the production database) → a novel's detail page (real summary text, real chapter list) → a chapter's full text (HTML correctly stripped to readable paragraphs). Every value on screen came from https://asterion-api.cyberverse.cloud, not placeholder data.
  8. Separately, the exact JSON shape of /novels, /novels/:id, and /novels/:id/chapters was fetched directly with curl and compared field-by-field against the Kotlin data classes, to confirm the parsing code matches the real backend contract and not just a guess at its shape.
  9. For anime, the same auth-bypass-then-revert technique was used again to tap through Home → Anime catalog (real cover art, real episode counts) → a title's detail page (real synopsis, real episode list) → an episode's actual video, confirmed playing by screenshotting real decoded video frames on screen — not just a "player ready" state with nothing visible. The player's own error log was read directly (not guessed at) to diagnose both the timeout and the 403, and each fix was re-verified by repeating the same tap-through afterward.
  10. For movies, the same pattern again: Home → Movies catalog (real posters, runtimes, years) → a title's detail page (real synopsis) → Play, confirmed by a screenshot of an actual decoded video frame — and confirmed a second time after the cleartext fix, since the first attempt at fixing it (allowing cleartext alone) still failed until the player's cross-protocol-redirect setting was also changed. Both fixes were verified by re-running the exact same tap-through, not assumed from reading the code.
  11. For football, Home → Football schedule (real fixtures) → a match's resolved stream list (real, per-language, per-quality options from a live POST) both verified with real screenshots showing real data. The final step — actually playing the embed — was tested honestly rather than declared working: two real fixes were verified to change the page's behavior (the storage error and the "aclib" reference error both disappeared from the console log after each respective fix), but the screen itself still shows the provider's own block message on every stream tried, including a different provider entirely. That remaining gap is reported as-is, not hidden.
